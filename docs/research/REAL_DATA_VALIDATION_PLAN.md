Статус: PROPOSED / NOT_EXECUTED. Исследована публичная документация; ни одного запроса за матчами, платного запроса или изменения production в этом этапе не было. Указанные ниже бюджеты — предлагаемые пределы эксперимента, а не подтверждённые лимиты аккаунта. Источники не утверждены.

## 2. Point-in-time: обязательное условие, не поле по догадке

Для каждой записи хранить локально provider ID, discipline, series/game ID, минимальные проверяемые поля, UTC received_at, время публикации поставщика (если документировано), schema version, hash и ссылку на разрешение хранения. API-ключи, headers, токены и сырые ответы с персональными данными не сохранять. received_at фиксируется в момент получения; его нельзя заменить временем завершения матча.

Нужны два независимых набора: предматчевые снимки участников/BO/состава и результаты с временем их доступности. Модель использует результат только после max(result ended_at, observation received_at, publication time). Снимок будущего/текущего состава нельзя переносить на старый матч. Исправления поставщика хранятся новой версией и не переписывают прошлое знание.

Если поставщик не выдаёт архив версий, исторический PIT-бэктест НЕВОЗМОЖЕН по свежей выгрузке. Альтернатива — разрешённое перспективное накопление снимков до матчей. Владелец должен согласовать длительность, хранение и квоту; автоматический сбор этим заданием не запускается. Существующий backtest CLI требует `prematchObservations`, историю результатов и датированные `rosters`; без них — abstention.

## 3. Последовательность эксперимента

1. Письменно подтвердить права: закрытый некоммерческий анализ, обучение/бэктест, хранение минимальных признаков, сроки удаления, показ пользователю. Отдельно спросить о будущем коммерческом использовании: интеграция LineRadar не включена в это разрешение.
2. Владелец выдаёт test/staging доступ через секреты окружения, не чат. Проверить тариф/остаток квоты в кабинете. Выбрать ОДНОГО поставщика для первой проверки.
3. Первый ручной probe: максимум 40 HTTP-попыток на выбранный API, включая 401/429 и повторы; без параллельного обхода, максимум 5/мин или меньший подтверждённый лимит. Резерв минимум 20% квоты. При неизвестном тарифе/цене — не запускать. Повторы только внутри общего бюджета; 401/403/ошибка схемы останавливают probe.
4. Диагностика: минимум 30 разных событий на дисциплину из 3 турниров, если объём ответа позволяет бюджет; отдельно предстоящие и законченные. Недобор честно указывается, бюджет не увеличивается автоматически. Выбрать 10 событий для повторной проверки ID/изменений, 10 результатов сверить с разрешённым независимым первичным источником. Ручное подтверждение ID, никакого нечёткого объединения названий.
5. Расширенная проверка схемы после разрешения: минимум 200 серий на дисциплину, включая BO1/3/5, переносы/отмены, неполные составы, новые команды, дубликаты/исправления. Невстреченный BO остаётся NOT_VERIFIED. Для карт отдельно минимум 50 игр с подтверждённой принадлежностью серии и результатом.
6. Проверка модели требует существенно больше данных: предлагаемый нижний порог 1000 train / 300 calibration / 500 независимых test-серий на дисциплину, строго по времени; это инженерный минимум, не гарантия статистической мощности. По каждому BO нужны отдельные sample sizes; малые группы не получают заявления о качестве. Оценить интервалы неопределённости и сравнение с 0.5/Elo baseline до выбора модели.

## 4. Что измерять и когда отклонять источник

Для discipline × tournament × BO: доступные события, доля валидных ID/дат/исходов, доля полных составов, полнота карт, доля PIT-снимков, расхождения независимой сверки, возраст и p50/p95 задержки результата, ошибки/429/объём HTTP. H2H вычисляется по точным ID из той же прошлой выборки; winrate карт только из подтверждённых game records. Нули не подставляются вместо отсутствующих значений.

Любое расхождение идентичности или временной причинности исключает запись; повторяющаяся системная проблема останавливает адаптер. Для закрытого пилота требуется отсутствие выдуманных полей и неразрешённых конфликтов, подтверждённые права и достаточное PIT-покрытие. Заранее выбранные пороги качества публикуются до просмотра test-метрик; их нельзя менять ради красивой точности.

## 5. Конкретное согласование с владельцем

- PandaScore: fixtures token для 40-запросного бесплатного probe; отдельно письменное sample/trial-разрешение на Historical по 4 дисциплинам, PIT архиву и хранению. Платный бюджет пока **0**.
- OpenDota: разрешение на ограниченный 40-запросный бесплатный эксперимент, проверка текущих квот и лицензии; ключ только если требуется действующим режимом. Платный бюджет **0**.
- GRID/Riot: регистрация владельца и non-commercial Open Access key + разрешение на выбранный use case, schema export и подтверждённый лимит. Платный бюджет **0**; будущая букмекерская интеграция запрещена этим режимом.
- Staging Supabase: отдельный проект/локальный disposable стенд, разрешение на применение миграций и двух тестовых пользователей. Production service-role не нужен и не запрашивается.
- До этих согласований: только mocks, локальные синтетические тесты, CI PostgreSQL и review. Статус продукта: NOT_READY_FOR_REAL_PILOT.
